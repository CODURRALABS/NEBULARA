# Chapter 11 — The VM & Bytecode

> Book: *Beyond the Bases* · Part IV — Inside the Engine

The **Virtual Machine (VM)** is the runtime heart of the interpreter. This
chapter looks at how it represents values and how it executes bytecode.

---

## The value model

The VM stores values as a **tagged union**. A `Value` is a struct with:

- a **tag** saying what kind it is (int, string, bool, null, array, function),
- and the **payload** — for an int the number, for a string a pointer to its
  characters, for an array a pointer to an array structure, etc.

This is the classic C way to get dynamic typing: one `Value` type, checked by
its tag at runtime. `TYPEOF(x)` is essentially the VM reading the tag.

```
struct Value {
    enum Type tag;       // INT, STR, BOOL, NULL, ARR, FUNC...
    union {
        int64_t i;       // when INT
        char   *s;       // when STR
        int    b;        // when BOOL
        Array  *a;       // when ARR
        ...
    } as;
};
```

---

## The array type

Arrays are their own structure with a capacity and length, because they grow:

```
struct Array {
    int64_t count;         // number of elements
    int64_t capacity;      // allocated slots (>= count)
    Value  *items;         // the element array
};
```

`PUSH` grows `capacity` when needed (realloc); `POP` decrements `count`;
`LEN` reads `count`. This is why `PRINT arr` shows `[array N]` — it's printing
the array's *type and count*, since there's no element-printing convention.

---

## Bytecode

The compiler emits a stream of instructions. The VM's main loop is a **switch
on the opcode**:

```c
for (;;) {
    switch (next_op()) {
        case OP_PUSH:  push(next_int());       break;
        case OP_ADD:   push(pop_int() + pop_int()); break;
        case OP_PRINT: print_value(pop());     break;
        case OP_CALL:  call_function(...);     break;
        case OP_RET:   return_from_frame(...); break;
        case OP_JMP:   jump_to(...);           break;
        ...
    }
}
```

Control flow (`IF?`, `WHILE?`, `FOR!`) compiles to **jumps**. `BREAK`/`CONTINUE`
compile to jumps to the end/next-iteration of the loop. Function calls push a
**call frame** so `RETURN` knows where to resume.

---

## The stack

The VM is **stack-based**: most operations pop operands and push results. This
makes the bytecode compact and the VM small — at the cost of some speed (which
is what native codegen optimizes away).

A function call creates a frame on the call stack holding its parameters,
locals, and the return address. This is why recursion has a finite depth —
frames pile up (Chapter 1).

---

## Builtins

The runtime builtins (`PRINT`, `LEN`, `ABS`, `READ_FILE`, ...) are wired into
the VM dispatch. The `nbs-bootstrap.c` "builtin functions" table maps each
name to a C implementation and its argument count. When you call `LEN(x)`, the
VM looks up the builtin, checks arity, and calls the C handler.

This is exactly where **verified-builtin lists matter** (like the cheat sheet):
only builtins present in the shipped table actually run. `SLEEP`/`ARGUMENT` may
be in source but absent from the builtin table of a given executable.

---

## The interpreter and FFI

The VM sits inside `nbs-bootstrap.c` (the `nebulara` interpreter). The FFI
subsystem integrates here: `FFI_CALL` is a builtin that bridges to native
libraries via `dlopen`/`LoadLibrary` and decodes values per the signature
(Chapter 8).

---

## Summary

- `Value` is a tagged union → dynamic typing via `TYPEOF`.
- Arrays are growable structs (count/capacity).
- The VM runs bytecode via an opcode switch on a value stack.
- Control flow = jumps; functions = call frames.
- Builtins are a name→C-function table with arity checks.
- Doc drift shows up here: unimplemented builtins aren't in the table.
